# 报告规范与评分

Phase 5 的产出标准。报告面向**产品/安全决策者 + 研发团队**两类读者：决策者看执行摘要与优先级，研发看漏洞详情与修复建议。

## 1. 报告结构（固定 7 区块，不得缺项）

配合 `assets/report-template.md` 使用。缺任何一区块都视为不合格交付。注意 ④ 与 ⑥ 的边界：**④ 只放已验证可达的漏洞，⑥ 只放未验证的组件 CVE 线索**，两者不可混。**组件风险条数不计入漏洞总数。**

### ① 执行摘要

- 目标设备型号、固件版本、下载来源、SHA256
- 攻击面概览：暴露的服务与端口数量、Web/CGI 入口数量、协议栈
- 漏洞统计表：按优先级（P0/P1/P2/P3）与置信度（**CONFIRMED / HYPOTHESIS** 两态）交叉计数
- **最严重的 3 条**：一句话描述 + 优先级 + 一句话影响（HYPOTHESIS 要标出「缺哪一步」）
- 一句话结论：这台设备的整体风险等级与最需要修的地方

### ② 目标与范围

- 镜像指纹：`SHA256`、大小、提取工具与版本
- 审计范围：T1/T2/T3/SKIP 文件数、EALB 总量、实际 Agent 数
- **覆盖率数字**（必须来自 `40-coverage.md`）：T1 100%、T2 x%、SKIP 关键字扫描 100%
- 未覆盖项清单及理由（例：加密分区未解密、需硬件触发的代码路径）
- 测试环境与限制（模拟环境 vs 真实设备、是否隔离）

### ③ 攻击面地图

| 面 | 内容 |
|---|---|
| 网络服务 | 端口、协议、进程、是否默认开启、是否需认证 |
| Web/CGI | 路由清单、鉴权状态（逐个标注） |
| 协议栈 | UPnP/HNAP/MQTT/CoAP/TR-069/私有协议 |
| 启动服务 | `init.d` 拉起的服务及其权限 |
| 云侧对接 | 域名、MQTT broker、证书使用方式 |
| 硬件接口 | UART/JTAG/SPI/USB 是否开放、是否可获 shell |
| 本地入口 | hotplug、USB 自动挂载、SD 卡、蓝牙配对 |

### ④ 漏洞详情（每条固定字段）

```markdown
### F-007 · CGI 未认证命令注入（ping 诊断接口）

- **类型**：command-injection (CWE-78)
- **位置**：`www/cgi-bin/ping.cgi` 反汇编 `0x2A30`（`usr/sbin/httpd` 内联处理）
- **优先级**：P0（DKTSS 10 / CVSS 9.8）
- **置信度**：CONFIRMED
- **CVSS 3.1**：`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H` = 9.8
- **IoT 修正**：Exposure ×1.0（WAN 可达）· AutoTrigger ×1.0（出厂默认开启、无需认证）· Impact ×0.9（设备完全接管）→ 8.82 起，含持久化加权后 9.3
- **DKTSS**：Base 10（命令注入可执行系统命令）− Friction 0（WAN/免认证/零交互）+ Weapon 1（有成熟 EXP）+ Ver 0 = **10**
- **成立条件判定**：Q1 代码存在 ✅（`@0x2A30` 定位 `bl system`）· Q2 路径可达 ✅（入口 `/cgi-bin/ping`，无鉴权分支）· Q3 输入可控 ✅（`ip` 来自 query，无白名单）· Q4 防护阻断 ❌（无 NX 但本链为命令执行，与内存防护无关）
- **Source**：HTTP `GET /cgi-bin/ping?ip=<可控>` → `recv()` @0x2870 → `sscanf` 提取 ip 参数 @0x2894
- **Sink**：`system()` @0x2A30，实参由 `sprintf(buf, "ping -c 1 %s", ip)` @0x2A1C 生成
- **完整调用链**：
  1. `handle_request` @0x2700
  2. `dispatch_cgi` @0x2850（**鉴权检查仅在 @0x2850 `beq` 的 /goform/ 分支内，本路径不经过**）
  3. `do_ping` @0x2A00
  4. `system` @0x2A30，无过滤（`ip` 未经过任何白名单）
- **前置条件**：无。设备默认开启 HTTP 于 80 端口
- **复现步骤**：
  ```bash
  curl -s "http://192.168.1.1/cgi-bin/ping?ip=1.1.1.1%3Bid"
  # 返回中包含 "uid=0(root)"
  ```
- **证据**：
  - 反汇编 `@0x2A1C`：`sprintf(buf, "ping -c 1 %s", ip)`
  - `@0x2A30`：`bl sym.imp.system`
  - Qiling hook 输出：`[SINK HIT] cmd = 'ping -c 1 1.1.1.1;id'`（见 `evidence/F-007-hook.log`）
  - 模拟环境命令回显：`evidence/F-007-curl.txt`
- **影响**：未认证远程代码执行，root 权限，可实现持久化（写 `/etc/init.d`）
- **修复建议**：
  1. 立即：`ip` 参数做白名单校验（仅允许 IPv4/IPv6 字面量），拒绝任何含 `;|&$\`` 与换行的输入
  2. 根本：改用 `execve` 传数组，不经 shell；或在 CGI 层做鉴权
  3. 加固：以非 root 用户运行 CGI；编译时启用 NX/PIE/Canary（见第 5 区块）
```

### ⑤ 加固与配置缺陷（非漏洞但影响整体风险）

这部分单独成节，因为它们**不是单点漏洞，但会放大所有漏洞的危害**：

- ELF 加固统计表（多少二进制无 NX / 无 PIE / 无 Canary / 无 RELRO）
- 硬编码凭据清单（值脱敏，只给指纹与位置）
- 调试接口开放情况
- 弱随机使用点
- 无验签的升级通道
- U-Boot env 可写 / 安全启动姿态（引用 `mithril --boot` 结果）
- 修复优先级建议（哪几条改了能显著提升整体安全水位）

### ⑥ 组件风险（未验证）—— 与漏洞章节严格分离

**为什么必须单列**：`mithril --cve` 做的是**版本比对**，它证明的只是「该组件的这个版本号落在某个 CVE 的影响版本区间内」。这与「固件里存在可被触发的漏洞」之间隔着至少五道缺口：

| 缺口 | 说明 | 反例 |
|---|---|---|
| 代码不存在 | 编译时裁掉了受影响组件 / applet / 模块 | BusyBox 命中数十条 CVE，但该 applet 未编译进来 |
| 已 backport | 厂商打了补丁但**没改版本号** | 大量路由器固件带 `1.31` 实为定制修复版 |
| 选项未开 | 漏洞需要编译期未启用的特性 | 需 `CONFIG_XXX`，固件未开启 |
| 配置未达 | 漏洞需要运行时不满足的前置条件 | 需 debug 模式 / 需特权进程可达 |
| 不可达 | 有漏洞代码，但没有任何输入路径能触达 | 函数存在但无调用者，或仅本地 socket 可达 |

**因此**：本节所有条目状态一律 `cve-hit`，措辞统一为「**疑似**…**尚未验证可达性**」。**禁止**：
- ❌ 把本节条数计入漏洞总数，或在执行摘要写「发现 N 个漏洞」
- ❌ 给 `cve-hit` 条目打 CVSS 或映射 P0-P3 优先级
- ❌ 写成「设备存在 XX 漏洞」「可被 XX 攻击」

**升级路径**：只有完成下列三项检查之一，条目才能移入 ④ 漏洞详情：
1. **代码在**：在固件内定位到受影响函数/签名（字符串、符号、反编译特征）
2. **可达**：从外部输入入口追出调用链（xref 链路），满足漏洞的前置条件
3. **确认未修复**：补丁特征不存在（对比厂商新版固件 / 检查关键分支是否缺失）

升级后重标状态：仅 (1)+(2) → `cve-reachable`（措辞「存在 CVE-XXXX-YYYY，可达路径为…」）；再经动态复现 → `cve-exploitable`（措辞「可被利用」）。

本节排序按 `CISA KEV 优先 → EPSS 降序`，定位为「**值得优先验证的线索清单**」，明确告诉读者「这些不是结论，是下一步该查什么」。

#### ⑥ ↔ ④ 迁移规则（与 Phase 4 联动）

`cve-hit` 不是终点，而是一张「待验证工单」。Phase 4 的职责之一就是把 ⑥ 里的线索逐条推进；**验证通过的条目必须「移动」，不是「复制」**：

| 阶段 | 触发 | 动作 | 状态 / 措辞 | 统计变化 |
|---|---|---|---|---|
| 初始 | `mithril --cve` 版本命中 | 仅登记进 ⑥ | `cve-hit`｜「疑似…尚未验证可达性」 | ⑥ 线索 +1，**不进漏洞总数** |
| 静态升级 | Phase 3/4 完成 (1)代码在 (2)可达 (3)未修复 | **移入 ④**（新 `F-0xx`），从 ⑥ 删除 | `cve-reachable`｜「存在 CVE-XXXX-YYYY，可达路径为…」 | ④ +1（按铁律 4 定 CONFIRMED / HYPOTHESIS），⑥ 未验证 −1 |
| 动态升级 | 动态复现 / 完整利用链 | 就地更新该 `F-0xx` | `cve-exploitable`｜「可被利用」 | 置信度升 `CONFIRMED`，优先级可上调 |
| 排除 | Phase 4 判定代码不存在 / 已 backport / 不可达 | 从 ⑥ 移入 `30-findings-verified.md` 的 `NOT_FOUND` 台账，⑥ 内注明「已排除（原因）」 | `cve-nonreachable` | ⑥ 未验证 −1，**不进漏洞总数** |

**「移动」的三条硬约束**（前两条由门禁 `coverage_gate.py --report` 的 **V4** 机械校验）：

1. 同一 `CVE-ID` **不得同时**作为 ④ 的 `F-0xx` 与 ⑥ 的未验证线索存在——两处并存即「复制」，会造成重复计数；
2. ⑥ 里允许保留一行指向 ④ 的**指针**（须含「已升级 / 已迁移 / → F-0xx」措辞），该行**不计入 ⑥ 的线索条数**；
3. 迁移后必须同步更新 **执行摘要的统计表** 与 **④ 的优先级分布**——只改条目、不改统计，等于报告自相矛盾。

> 统计口径一句话：**漏洞总数 = ④ 条目数（CONFIRMED + HYPOTHESIS）**。⑥ 无论有多少条 `cve-hit`，都不进这个数；Phase 4 每升级一条，④ 与 ⑥ 同时 `+1 / −1`。

### ⑦ 附录

- 工具与版本清单（可复现性）
- 关键命令回放（Phase 0-5 的实际命令）
- 规则文件（`50-rules/` 内容索引）
- 敏感信息位置索引（路径 + 指纹，**值脱敏**）
- 术语表（可选）

## 2. 字段与格式规范

### 位置标注格式

| 场景 | 格式 | 示例 |
|---|---|---|
| 二进制代码 | `文件:0x偏移` | `usr/sbin/httpd:0x2a30` |
| 源码/脚本 | `文件:行号` | `etc/init.d/rcS:42` |
| 固件分段 | `文件:0x偏移(长度)` | `firmware.bin:0x1a0000(0x400000)` |
| 文件系统内路径 | 相对 rootfs 的路径 | `www/cgi-bin/ping.cgi` |

**禁止**用含糊表述（「大致在 httpd 里」「某处代码」）。

### 证据引用格式

```
[E1] disasm usr/sbin/httpd@0x2a1c
     2a1c:  e59f1018  ldr r1, [pc, #24]      ; "ping -c 1 %s"
     2a20:  e1a00004  mov r0, r4
     2a24:  ebffffd3  bl  sprintf
[E2] strings -tx usr/sbin/httpd
     1c40  ping -c 1 %s
[E3] qiling hook log evidence/F-007-hook.log:12
     [SINK HIT] cmd = 'ping -c 1 1.1.1.1;id'
[E4] curl 回显 evidence/F-007-curl.txt:3
     uid=0(root) gid=0(root)
```

每条 finding 至少两条独立证据（静态 + 动态/交叉验证）。

### 脱敏规范

| 类型 | 处理 |
|---|---|
| 私钥 | 只给类型 + 指纹（`SHA256:ab12cd34…`）+ 路径 |
| 口令/口令哈希 | 只给路径与算法（`/etc/shadow:root → MD5-crypt`），不给值 |
| 云 token / AK | 只给前缀 4 位 + 长度 + 路径（`AKIA…（20 字符）`） |
| 会话 token | 只给路径与格式 |
| 证书 | 只给 CN、指纹、路径 |
| 内网 IP / 域名 | 可保留（属于攻击面信息），但标记为非敏感 |

完整值写入 `50-secrets.local`，不随报告分发。**报告中任何一条都不能让人直接拿去登录。**

## 3. IoT 语境评分表（可复制到报告）

```
漏洞 ID:  F-xxx
CVSS 3.1:  AV:N / AC:L / PR:N / UI:N / S:U / C:H / I:H / A:H   = 9.8
IoT 修正:
  Exposure      [ ] WAN ×1.0   [ ] LAN ×0.8   [ ] 邻接 ×0.6   [ ] 物理 ×0.4   → 1.0
  AutoTrigger   [ ] 默认开启无需交互 ×1.0  [ ] 需认证 ×0.7  [ ] 需用户操作 ×0.4  [ ] 需特殊构造 ×0.2  → 1.0
  Impact        [ ] 持久化+绕过安全启动 ×1.0  [ ] 设备完全接管 ×0.9  [ ] 沙箱内执行 ×0.6  [ ] 信息泄露 ×0.4  [ ] DoS ×0.2  → 0.9
实战分值 = 9.8 × 1.0 × 1.0 × 0.9 = 8.82  →  P0
```

优先级映射：`≥8.0 → P0`、`6.0-7.9 → P1`、`4.0-5.9 → P2`、`<4.0 → P3`。

**避免优先级通货膨胀**：P3 必须在报告里明确写「低优先，不影响量产决策」。把所有东西都标 P0 的报告等于没有优先级。

## 3.1 DKTSS 评分（实战阻力修正，与 IoT 修正并行）

上面的「IoT 修正」是**乘法**模型（CVSS × 三个系数），适合快速三档排序。但它在两个地方会失真：**（a）** 一堆漏洞乘完后挤在 8.0 上下，区分度不够；**（b）** 「需要管理员登录」这类**关键阻力**被 CVSS 忽略（CVSS 给 8.8 High，实战成本却高得多）。

**DKTSS（DarkKnight Threat Scoring System）** 是**加减法**模型，把利用成本显式扣出来，更适合给一批漏洞排真实修复顺序。**固件场景下建议用它做主排序，CVSS/IoT 修正作为并列展示。**

### 公式

```
DKTSS = min(10, Base − Friction + Weapon + Ver)
```

### Base（按类型 + 实际影响，不是简单「RCE=10」）

| 漏洞类型 | 条件 | Base |
|---|---|---|
| RCE / 命令注入 | 可执行系统命令 | 10 |
| RCE / 反序列化 | 仅代码执行（无命令） | 9 |
| 固件升级无验签 | 可刷任意固件（等价持久 RCE） | 10 |
| 认证绕过 | 可访问管理后台 / 可改配置 | 8 |
| 认证绕过 | 仅访问普通功能 | 5 |
| 路径穿越 | 可写任意文件 | 8 |
| 路径穿越 | 可读任意文件（如 `/etc/shadow`） | 6 |
| 内存破坏 | 可控执行流（PIE 关闭 / 可 ROP） | 9 |
| 内存破坏 | 仅崩溃 DoS（不可控 PC） | 3 |
| SSRF | 可访问内网 / 云元数据 | 7 |
| SSRF | 仅 HTTP 无回显 | 4 |
| 文件上传 | 可传 webshell 且目录可执行 | 9 |
| 文件上传 | 仅上传恶意文件（需结合其他漏洞） | 5 |
| 硬编码凭据 | 影响全型号设备（对称密钥 / 通用口令） | 8 |
| 硬编码凭据 | 仅单台设备（如设备唯一序列号派生） | 4 |
| 敏感信息泄露 | 口令 / API Key / Token | 6 |
| 敏感信息泄露 | 内部 IP / 配置信息 / 版本串 | 3 |
| 配置篡改 | 未授权改安全配置（关防火墙 / 开 WAN 管理 / 改口令） | 7 |
| 配置篡改 | 仅改非安全配置 | 3 |
| 拒绝服务 | 远程一键重启 / 断网（需刷机才能恢复） | 6 |
| 拒绝服务 | 仅资源耗尽 / 降速（可自愈） | 3 |
| 供应链 / 第三方组件 | 组件缺陷可被外部可达利用 | 7 |
| 供应链 / 第三方组件 | 组件版本过期但代码不可达 | 3 |
| 云对接鉴权缺失 | 可下发指令 / 接管他人设备（MQTT / 云 API / TR-069） | 8 |
| 云对接鉴权缺失 | 仅可读他人数据 / 越权订阅 topic | 5 |
| 越权 / 业务逻辑绕过 | 跨设备 / 跨用户越权，或仅前端校验（后端缺失） | 7 |
| 弱随机 / 可预测令牌 | 会话 / 重置令牌 / 密钥可预测 → 账户接管 | 7 |
| CSRF | 管理接口可被跨站触发改配置 | 6 |
| 调试接口 / 后门 | 未授权 shell 或命令执行接口 | 10 |
| 安全启动绕过 / 持久化 | 可持久化并绕过信任链（改 bootargs / 刷固件） | 10 |
| 传输安全降级 / MITM | 可拦截 / 篡改加密流量，或降级至明文传输 | 6 |
| 不安全临时文件 / 本地提权 | 可预测或可写的临时路径影响特权流程（root / 守护进程） | 7 |

**兜底规则（防评分落空）**：Base 表**不要求穷举**，但要求**可映射**——报告中出现的每一种漏洞类型（标签来自 `vuln-conditions.md` 的 10 类或 `vuln-taxonomy.md` 的分类）都**必须**能命中本表某一行；**命中不到时，按「最接近类型的实际影响」对齐，并在报告中写明映射依据**，不得留空、也不得凭感觉给分。`coverage_gate.py --report` 可扩展为对报告中出现的每个类型标签做 Base 表命中校验。

### Friction（实战阻力，三项独立累加后从 Base 扣除）

| 维度 | 条件 | 值 |
|---|---|---|
| **访问路径** | WAN / 互联网可达 | 0 |
| | 需内网 / VPN / 同网段邻接 | −2 |
| | 需物理接触（UART / SPI / 拆机） | −4 |
| **权限门槛** | 无需认证（预认证） | 0 |
| | 需低权限账号 | −1 |
| | 需管理员账号 | −3 |
| | 需特定角色 / 特定条件 | −2 |
| **交互复杂度** | 零交互（单次请求触发） | 0 |
| | 弱交互（需点击 / 需访问页面） | −1 |
| | 强交互（多步操作 / 社会工程 / 需竞态） | −3 |

### Weapon（现成利用工具）

| 条件 | 值 |
|---|---|
| 有成熟 EXP（Metasploit / Nuclei / 公开完整 EXP） | +1 |
| 仅有 PoC 代码 | 0 |
| 需特定环境 / 特定配置 | −1 |
| 仅理论分析 / 需竞态 / 需先满足其他漏洞 | −2 |

### Ver（版本因子）

| 条件 | 值 |
|---|---|
| 当前固件版本存在漏洞 | 0 |
| 厂商已有补丁固件但目标未升级 | +1 |
| 仅旧版本存在（需确认目标版本） | −1 |

### 等级映射（响应时效）

| DKTSS | 等级 | 响应 |
|---|---|---|
| 9-10 | Critical | 立即修复（24h） |
| 7-8 | High | 优先修复（7 天） |
| 5-6 | Medium | 计划修复（30 天） |
| 3-4 | Low | 低优先（90 天） |
| 0-2 | Info | 可接受 / 观察 |

### 为什么固件场景特别需要它

| 场景 | CVSS 给的分 | DKTSS 的真实成本反映 |
|---|---|---|
| 需拆机接 UART 才能触发的 root 命令注入 | 9.8（Critical，虚高） | `Base 10 − Friction 4（物理）= 6`（Medium） |
| 同网段可打的内存破坏 | 8.1（High） | `Base 9 − 2（需邻接）= 7`（High） |
| 需管理员登录的 CGI 注入 | 8.8（High，虚高） | `Base 10 − 3（需管理员）= 7`（High，但排序后移） |
| 无验签 OTA + WAN 可达 + 免认证 | 9.8 | `Base 10 − 0 + 1（有 EXP）= 11 → 10`（Critical） |

**关键**：固件漏洞的差异**几乎全在 Friction**——同一段代码，WAN 可达 vs 需拆机，实战价值差一个数量级。DKTSS 把这个差异显式建模。

### 使用规则

1. **先定 Base**（查表，按实际影响不按类型名）
2. **算 Friction**（三项相加）
3. **评 Weapon**（有没有现成 EXP）
4. **定 Ver**（当前版本是否受影响）
5. **`Score = Base − Friction + Weapon + Ver`，上限 10**
6. **只对 `CONFIRMED` 评分**。`HYPOTHESIS` 不评分、不进优先级分布（见 §3 末条与 `methodology.md` §4）
7. 无法确认的条件**标注「需进一步确认」，不可猜**

**报告呈现**：在 ④ 漏洞详情的「优先级」字段里并列给出，例如 `P0（DKTSS 9 / CVSS 9.8）`；当两者冲突时（CVSS 高但 DKTSS 低），**以 DKTSS 排序为准**并在报告中说明差异原因（通常是 Friction 高）。

## 4. 常见报告缺陷（自查清单）

- [ ] 有没有把 `HYPOTHESIS` 写成 `CONFIRMED`？（应为「疑点」+ **写明缺哪一步**）
- [ ] 每条 finding 有没有 9 个必填字段（类型/位置/优先级/置信度/CVSS 3.1/Source/Sink/完整调用链/证据）？跑 `coverage_gate.py --report` 自动查
- [ ] 标题里有没有评级括注（`(Critical)`）？（应放「优先级」字段）
- [ ] 每条 finding 有没有至少两条独立证据？
- [ ] 有没有出现无 `文件:偏移` 的描述？
- [ ] 有没有把 `mithril --cve` 的组件命中直接写成「设备存在该漏洞」？
- [ ] 每条 finding 有没有过 `vuln-conditions.md` 的「通用四问」（代码存在/可达/可控/防护）？
- [ ] 覆盖率数字是否来自 `coverage_gate.py`，而不是估的？
- [ ] 审阅清单是否逐项打勾，且与结论一致（无 G1/G2/G3）？
- [ ] 未覆盖项有没有写明理由？（写「未覆盖」但不写理由 = 不合格）
- [ ] 凭据是否全部脱敏？
- [ ] 修复建议是否可执行（具体到函数/行/配置项，而不是「加强输入校验」）？
- [ ] 有没有 DoS 被写成 RCE？
- [ ] 优先级是否以 DKTSS 排序（而非 CVSS）？CVSS 高但 DKTSS 低的条目有没有说明原因？
- [ ] 复现步骤能不能让第三方照着做出来？
- [ ] 工具版本与命令是否完整（可复现性）？
